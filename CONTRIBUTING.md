# Contributing to py-overload

Thank you for your interest in contributing. This document explains how contributions are handled, how to report issues, and the policies that apply to human and automated contributions.

## Quick summary

- This repository is licensed under CC BY‑ND 4.0, which includes a NoDerivatives clause. See `LICENSE.md` for details.
- Direct modifications to source code are only accepted from listed maintainers.
- If you are not a listed maintainer, please open an issue describing the bug or feature request rather than submitting a pull request.
- Approved dependency-update automation (for example, `dependabot[bot]` or other automation explicitly installed and authorized by the repository owner or maintainers) is allowed for dependency maintenance updates only.
- Pull requests that contain code generated by AI tools are not accepted from non-maintainers. Maintainers must explicitly declare any use of AI tools in PR descriptions.

## How to report bugs or request features

- Open an issue with a clear title and steps to reproduce (if a bug) or a clear description of the desired behavior (if a feature).
- Include:
  - Python version
  - operating system
  - minimal reproduction code or test
  - relevant tracebacks or CI output

## Contributor types

- Maintainers: listed maintainers may open and merge pull requests that modify source code.
- Collaborators: users with explicit write/collaborator access may open in-repo PRs.
- External contributors (non-collaborators): please open an issue first. PR creation from forks or non-collaborators is restricted by repository policy.

## Pull request policy

### Maintainers and collaborators
- Base your work on a feature branch named like:
  - `maintainer/<short-description>`
  - `dependabot/<package>-<version>` for approved automation branches
- Each PR must include:
  - a brief description of the change and motivation
  - a link to the related issue, if any
  - a clear statement whether any part of the PR was generated by an AI tool
  - tests demonstrating the change, where appropriate
  - documentation updates if behavior changes

### Required checklist for maintainers
- [ ] Tests added/updated and passing locally.
- [ ] CI checks are green.
- [ ] Documentation updated if the API/behavior changed.
- [ ] No breaking changes, or breaking changes are documented and approved.
- [ ] PR body declares whether AI tools were used.

## AI-generated content policy

- Human-authored PRs from non-maintainers that include code generated by AI tools (Copilot, Codex, ChatGPT, Claude, etc.) will be closed without review.
- Maintainers may use AI tools, but must:
  - declare which tool(s) were used in the PR description
  - manually review and verify all generated code for correctness, tests, style, and license compatibility
- This policy exists to respect the NoDerivatives clause of the repository's declared license and maintain code quality.

## Dependency automation and bots

Approved dependency-update automation is allowed and will be reviewed by maintainers.

Allowed examples:
- GitHub Dependabot
- Renovate
- other dependency-update tools explicitly installed and authorized by the repository owner or maintainers

These automation PRs must:
- be limited to dependency version updates, lockfile updates, or metadata changes required by the dependency update itself
- not change project logic or source-code behavior beyond what is required for the dependency update
- be reviewed by maintainers before merge

The following are not accepted:
- source code pull requests from non-maintainers
- AI-generated source code changes from non-maintainers
- dependency-update PRs that go beyond the scope of dependency maintenance and introduce project logic or behavioral changes

If you are installing a third-party dependency manager (Renovate, etc.), make sure it is granted write access to this repository so it can open in-repo branches and PRs.

## Security

- For security vulnerabilities, please use the GitHub Security Advisories flow or contact the maintainers privately if you prefer confidential disclosure.
- Do not open public issues containing exploit code that could put users at risk.

## Code style, tests, and tooling

- Follow existing style in the repository (PEP 8 where appropriate).
- Run the test suite locally before opening a PR.
- Keep changes minimal and focused per PR. Large, multi-area changes should be split into smaller PRs.

## How to request collaborator access

- If you believe you should be a collaborator or maintainer, open an issue titled `Access request: collaborator` and include:
  - your GitHub username
  - a short justification
  - examples of prior contributions or relationship to the project

## Merging and releases

- Only maintainers may merge PRs to the default branch.
- Releases are created by maintainers and follow the repository's release process.
